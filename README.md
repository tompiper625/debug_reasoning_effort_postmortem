# REASONING_EFFORT 排查复盘：一个从未生效的"幽灵环境变量"

> 我以为写上 `REASONING_EFFORT=max` 就能满血推理。抓包证明：这个变量从未离开过我的电脑。

## 一、遇到的问题

今天我开通了 Kimi API，用它的 Anthropic 兼容端点接入 Claude Code。我先读了 Kimi 的 API 文档，了解到模型的推理强度分三个等级：low / high / max。既然要用，我当然选最高等级 max。

问题出在"怎么把这个选择告诉模型"：文档里写了档位，却没写在 Claude Code 这种 Anthropic 协议客户端里，该用**哪个环境变量**把它传过去。没有明确的变量名可依，只能凭直觉写一个看起来最合理的：

```json
"REASONING_EFFORT": "max"
```

文档里的最高档叫 max，那就 `REASONING_EFFORT` 设成 `max`，还能有错？

配置写进去之后，一切"看起来"都正常：没有报错、没有警告、对话照常进行。但反过来想，我也**没有任何证据**证明它生效了——没有日志、没有反馈、没有地方能查看"当前推理档位"。

一个文档里没人认领的配置，配上一个无法观测的效果，疑问自然就来了：**这个变量，API 那一端真的收到了吗？**

中间隔了一层客户端、一层协议转换。配置写在本地，生效在远端——这中间任何一个环节把这个字段丢掉，我都不可能有任何感知。没有报错，恰恰是最大的隐患。

## 二、我如何解决的

### 思路：与其猜，不如抓包

客户端到底发了什么，靠猜、靠文档、靠问 AI 都不算数——**在本地起一个代理，把请求体原样记录下来**，让数据自己说话。

我让 AI 帮我写了一个 50 行的 Python 转储代理（[dump_proxy.py](dump_proxy.py)）：

1. 在 `127.0.0.1:8399` 监听，把 `ANTHROPIC_BASE_URL` 指过来；
2. 每个请求体里挑出 `thinking`、`output_config`、`reasoning_effort`、`reasoning`、`model` 这几个字段，连同全部顶层字段名一起记进 JSONL；
3. 原样转发给真实上游，不影响正常使用。

然后做了三组对照实验，每次只改一个变量，发一条同样的消息：

| 实验 | 配置 | 抓包结果 |
|---|---|---|
| ① 我的日常配置 | `REASONING_EFFORT=max` | `output_config: {"effort": "high"}` ← **默认值** |
| ② 换成官方变量 | `CLAUDE_CODE_EFFORT_LEVEL=max` | `output_config: {"effort": "max"}` ✅ |
| ③ 空白对照 | 两个都不设 | `output_config: {"effort": "high"}` |

原始记录见 [evidence/request_dump.jsonl](evidence/request_dump.jsonl)。

### 结论

三条记录摆在一起，事实无可辩驳：

- **`REASONING_EFFORT` 根本不是 Claude Code 的官方环境变量。** 它被客户端完全忽略——请求体里没有 `reasoning_effort` 字段，`effort` 始终是默认值 `high`。实验①和实验③的请求体一模一样，这个变量设与不设毫无区别。
- **真正的官方变量是 `CLAUDE_CODE_EFFORT_LEVEL`**（取值 low/medium/high/xhigh/max/auto），它会被映射为请求体里的 `output_config.effort`，配合 `thinking: {"type": "adaptive"}` 的自适应思考模式一起发出。
- 第三方端点（Moonshot）接受 `effort: "max"`，返回 200，没有 400——链路是通的，错的一直是我写的变量名。

修正方式：把 `settings.json` 和预设文件里的 `REASONING_EFFORT` 全部改成 `CLAUDE_CODE_EFFORT_LEVEL`。

## 三、引发的思考复盘（重点）

### 同样用 AI 辅助 debug，效率可以天差地别

这次 debug 我全程依赖 AI 智能体，最终问题解决了，但过程惨不忍睹——**真正花在定位和验证上的时间可能只有二十分钟，而大部分时间白白消耗在了"调试工具本身"上**。

复盘整个过程，我踩的坑主要有三个：

**1. 我把智能体当成了唯一的执行者，结果被它的"安检系统"单点锁死。**

Claude Code 在自动模式下，每次执行 Bash/Write/Edit 前都要过一道 LLM 安全分类器，而分类器的推理恰好也跑在我配置的那个模型 API 上。偏偏那天晚高峰，模型端点严重劣化——聊天流式传输还能勉强用，但有严格超时的分类器反复超时、fail-closed，把智能体的每一步操作都卡死：写脚本卡一次、启动代理卡两次、改配置卡三次……

智能体反复重试、反复被拒，我在旁边反复等待。现在回头看，这是最愚蠢的一段：**我自己就有终端，分类器卡的是 AI，又不是我。** 如果早一点把分工改成"AI 出方案、我动手执行"，至少能省下一半时间。

**2. 我做了"动态实验"，却没先做"静态检查"。**

抓包实验是正确答案，但它是第二答案。第一答案其实更便宜：`REASONING_EFFORT` 是不是官方变量，在本地的客户端代码里 grep 一下这个名字就知道——搜不到，就说明客户端根本不认识它，一分钟结案，连代理都不用起。

一个高级程序员面对"配置是否生效"这类问题，排查顺序一定是：**先静态（代码里有没有消费这个变量）→ 再动态（请求里有没有这个字段）→ 最后才是端到端（远端有没有响应）**。我直接跳到了第二层，虽然也得到了结论，但方法论上是侥幸。

**3. 环境知识的欠缺让我绕了一个大弯。**

实验第一轮什么都没抓到，因为我用 `ANTHROPIC_BASE_URL=... claude -p` 的方式在命令行前置环境变量，而 `settings.json` 里的 `env` 块优先级更高，直接把它覆盖了——流量根本没走我的代理。这种"配置优先级"的知识，懂的人一秒指出，不懂的人要 debug 半小时。

### 如果是一个高级程序员，他会怎么做

我设想了一下同样的起点、同样的 AI 助手，一个经验丰富的人会怎样处理：

- **先问最便宜的问题**："这个变量名官方文档里有吗？本地 cli.js 里搜得到吗？"——一次 Read/Grep，不触发分类器，不需要网络，不需要模型状态良好。大概率到这里就结束了。
- **第一次被分类器卡住时就换路线**，而不是像我一样看着它重试三四次。AI 的执行通道是多路的：它能写文件让我跑、能把命令贴给我执行、能做纯只读分析。一条通道堵塞，立刻切换，而不是在原地等待。
- **把人机分工用在刀刃上**：让 AI 做它擅长的（写脚本、分析数据、解释原理），让人做人擅长的（在自己终端里跑命令、改自己电脑上的配置）。我这次最大的浪费，就是让 AI 卡在"它没有权限/通道执行"的事情上空转，而我这个"有权限的人"在旁边干等。
- **对"沉默的失败"保持本能警觉**——这可能是最重要的一条。`REASONING_EFFORT` 最恶劣的地方不在于它无效，而在于它**无效得毫无声息**。高级程序员对"配置即信仰"天然不信任：凡是看不到效果反馈的配置，都默认它没生效，直到拿出证据。我正好相反——写下 `REASONING_EFFORT` 的那一刻，我就把"没报错"当成了"已生效"。如果今天没有起疑心抓包，这个幽灵变量会无声无息地留在我的配置里，也许一年都不会被发现。

### 一句话总结

> AI 智能体能放大一个程序员的调试能力，但放大的是"已有的方法论"，而不是替代方法论本身。有章法的人用它一日千里，没章法的人用它——只是把"瞎试"自动化了而已。

这次踩坑教会我的三件事：**静态检查优先于动态实验；执行通道被卡立刻换路而不是等待；以及，任何没有可观测反馈的配置，都值得怀疑。**
